# v1.11.0 — Confirmações seguras e consistência financeira

**Publicada em 24/10/2026 (UTC)**, após CI, deploy e health checks aprovados.
[Release no GitHub](https://github.com/BryanPinheiro77/FinanceBot-BackEnd/releases/tag/v1.11.0).
Versão anterior: v1.10.1.

## Novidades e correções

- `Idempotency-Key` opcional nas criações REST de transações/parcelamentos: replay
  retorna a resposta original; conflito de conteúdo retorna `409`.
- Confirmações Telegram conservam a chave durante retries e, no modo Redis,
  retomam a pendência após reinício. Após uma tentativa, o conteúdo fica congelado.
- Parcelamentos preservam centavos e não geram parcelas zeradas/negativas por
  arredondamento; a prévia reutiliza o mesmo plano da criação.
- Novos usuários começam com resumos semanais/mensais desativados e recebem
  orientação sobre `/alertas`; preferências anteriores são preservadas.

## Segurança e operação

- Limites por IP em login/cadastro, com Redis, `429`, `Retry-After` e falha fechada
  `503` quando o contador estiver indisponível.
- Isolamento entre usuários validado com JWT e tentativas cruzadas de acesso/escrita.
- Builds restritos em estágios, JRE 21 com somente o JAR em `/app` e UID/GID 10001.
- Portas HTTP da API e do bot publicadas somente em loopback. Consumidores que
  usavam IP:porta do host devem usar o proxy HTTPS ou acesso administrativo autorizado.
- API e bot alinhados ao Spring Boot 4.0.9; cliente RabbitMQ 5.37.0.
- Variantes `.env.*` fora do Git; exemplos continuam disponíveis.

O frontend e a landing page têm repositório/publicação próprios e não integram os
artefatos desta release do backend.

## Migrations e configuração

- **V16** altera somente os defaults dos resumos para novos usuários.
- **V17** cria o armazenamento transacional de idempotência, com respostas cifradas
  pelo chaveiro existente, retenção e limpeza em lotes. Não há novos secrets obrigatórios.
- Redis passa a ser necessário para login/cadastro. Verificar credenciais, acesso
  a scripts Lua e timeouts; não desabilitar a proteção para contornar falhas.
- Confirmar a topologia do proxy e `FINANCEBOT_AUTH_TRUSTED_PROXIES` antes do deploy.
  Confiar somente nos proxies controlados; sem configuração, visitantes de um mesmo
  proxy compartilham cota. Não habilitar reescrita antecipada do IP pelo servidor.
- Publicar **API antes do bot**. O bot novo depende do contrato de idempotência da
  API nova. Usar `TELEGRAM_STATE_STORE=redis` para retomar pendências após reinício.
- Mounts de escrita adicionais devem permitir UID/GID 10001. Configuração real
  permanece no `.env` protegido do operador, fornecido ao processo pelo Compose.

## Evidências de preparação

- 550 testes da API e 200 testes do bot aprovados com `clean verify` na preparação.
- Duas verificações Docker aprovadas: exclusões do contexto, JAR e execução sem root.
- Consulta OSV em 24/10/2026: 171 combinações pacote/versão de runtime, nenhum aviso
  retornado após as atualizações. Não é um certificado de ausência de vulnerabilidades.
- Backup PostgreSQL e chaveiro criptografados, com cópia fora do servidor e checksum
  conferido. Restauração em PostgreSQL 17 temporário, com rede isolada e limites
  de recursos: contagens conferidas contra o snapshot consistente.
- SQLs V16/V17 exercitados sobre a cópia restaurada, preservando as preferências
  anteriores. Esta verificação não substitui executar o Flyway da aplicação no deploy;
  as suítes de integração também validam as migrations com PostgreSQL real.
- Os dados, caminhos, chave de backup e observações de rede ficam em registro privado.

## Recuperação e pendências

Antes da publicação, preservar a cópia do backup e a chave correspondente fora do
servidor, com acesso restrito. Falhas de deploy devem ser avaliadas antes de rollback:
voltar a imagem não desfaz migrations; nenhuma restauração sobre produção é automática.
O backend anterior já tem isolamento no domínio, mas não oferece o contrato de
idempotência do bot novo: reverter os dois módulos de forma coordenada.

A rotina contínua de backup/restore (#220), isolamento operacional (#219) e
manutenção do host/runner (#221) seguem abertas; o backup pontual não encerra essas
frentes. Não apagar imagens/caches nem revogar chaves de dados indiscriminadamente.
